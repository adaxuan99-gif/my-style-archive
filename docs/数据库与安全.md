# 数据库与安全

## 已实现的数据结构

| 表 | 保存内容 | 关系与约束 |
| --- | --- | --- |
| auth.users | Supabase 管理的账号 | 不自行保存密码 |
| garments | UUID、用户、稳定编号、资料 data、版本、创建/修改时间 | 每用户编号唯一；名称、分类等约束；每次编辑版本 +1 |
| photos | UUID、用户、衣服 UUID、存储路径、字节数、宽高、顺序 | 衣服+用户联合外键；不能跨用户关联；第 0 张是封面 |
| profiles | 当前风格资料、版本、修改时间 | 每用户一份；乐观锁保护 |
| categories | 自定义一级分类 | 用户+名称唯一 |
| number_counters | 每个用户、每种前缀的最大使用编号 | 删除衣服不会降低计数；恢复同步提升 |

衣服资料 data 为有校验的 JSONB（PostgreSQL 原生结构化字段），包含名称、分类、二级分类、颜色、版型、材质、厚度、季节、标签、品牌、尺码、价格、购买日期、渠道、手工频率备注、喜爱度、闲置、状态、备注和归档标记。用 TypeScript/Zod 定义完整输入规则，数据库对核心字段、大小和合法状态再约束。金额以人民币元记录。

采用结构化 JSONB 是为个人档案迭代保留灵活性；用户、唯一编号、照片、关联、版本仍是关系型列。后续高频统计字段可迁移为独立列，无需丢失原始资料。

## 编号策略

裤子 P、上衣 T、鞋 S、外套 O、裙子 K、连衣裙 D、包 B、帽 H、首饰 J、其他配饰 A、其他/自定义 X。每类从 001 开始，超过 999 正常增长。UUID 才是内部主键，编号供人阅读。

编号只由数据库保存函数创建；计数器更新是原子操作。换分类保留原编号；删除不重排、不复用。恢复 ZIP 同时恢复计数器，连“曾经有、后来删除”的编号也不会复用。

## 手机页面结构

底部五栏：我的衣柜 → 穿搭实验室 → 风格档案 → 穿搭日记 → 我的。衣柜优先展示筛选与衣服；录入与详情用底部弹层。第二阶段入口明确未开放。我的放备份、分类、存储清理、安装提示和退出，避免日常页面按钮过多。

## 权限边界

所有公开业务表都开启 RLS。RLS 指数据库每次查询时只允许读取当前账号自己的行，不能只靠前端隐藏别人内容。

- anon（没登录）没有私人表和保存函数权限。
- authenticated（已登录）只读自己的衣服、照片和档案；自定义分类写入也检查自己的用户 UUID。
- 衣服/档案修改通过 SQL 函数完成，直接表写入被撤销，防止绕过稳定编号与版本检查。
- 函数使用 SECURITY DEFINER，为完成原子操作使用受控权限；空 search_path、防对象替换；每次从 auth.uid() 取用户，不相信调用者传来的用户 ID；撤销 PUBLIC 执行权限。
- 所有照片和衣服通过联合外键绑定同一用户。
- 云端必须使用本仓库 SQL；只配置客户端而不执行 RLS 不构成安全部署。

## 照片安全

wardrobe 桶是 Private。照片键为 `用户UUID/照片UUID.jpg`。客户端下载带登录凭证，获得 Blob 后用内存 URL 展示；不创建公开地址，也不创建可转发的签名 URL。

知道另一个用户照片路径，不足以获得文件。退出、关闭页面、切换照片时释放 Blob URL。不把私人照片放到静态资源目录、网页分析服务或第三方图片代理。

上传在浏览器解码 → 可选裁剪 → JPEG 重编码，移除原照片 EXIF，最长边 1600px。原图最多 20MB，处理后最多 2MB，单件最多 12 张。Storage 同时限制 JPEG 类型与文件大小。存储服务以 MIME 判断类型；合法客户端重编码并在恢复时校验 JPEG 标记，不能把 MIME 限制理解为病毒扫描服务。

上传路径不允许覆盖，修改照片创建新 UUID。资料保存失败时尝试清理新文件；已关联的文件禁止直接删除，避免网络不确定状态误删已保存照片。超过 24 小时的未关联上传残留可在“我的”手动清理。

## 保存与失败处理

1. 上传完整照片。
2. 在一个 PostgreSQL 事务中保存衣服和照片关联。
3. 保存成功后清理替换的旧照片。

如果旧照片清理失败，资料依然成功，界面明确提示。Storage 和 PostgreSQL 无法跨服务成为同一事务，因此故障可能留下未关联照片，不能承诺完全无残留。不会先删照片再保存资料。

多设备编辑带版本号；过期版本拒绝覆盖。批量管理每件独立提交，部分失败提示已完成数量；再次读取后选剩余项重试。

## 后续阶段的数据结构（设计，尚未迁移）

第二阶段：

- outfits：用户、标题、季节、场景、标签、评分、原因、备注、创建时间。
- outfit_items：用户、穿搭 UUID、衣服 UUID、排列顺序；同类允许多件，以联合用户外键隔离。
- diary_entries：用户、日期、穿搭、场景、天气备注、满意度、舒适度。
- diary_items：当天实际衣服快照，记录固定关联，避免后续编辑穿搭改写过去穿着次数。
- diary_photos：私有照片，使用单独资源类型与同样的权限模式。
- shopping_candidates：商品属性、状态、价格、品牌、链接、喜欢原因、决策及原因。
- shopping_matches：候选与实际库存的手动相似确认。

第三阶段：

- inspirations + inspiration_photos：独立灵感图库，不作为拥有的衣服。
- style_preferences：喜欢/不喜欢、内容、原因、创建与修改时间。
- style_snapshots：按阶段追加的风格总结，旧版本不覆盖。
- ai_feedback：日期、对象类型及 UUID、文本、是否认同、用户补充。

每张新表必须同时写 RLS、联合用户外键、备份导出/恢复迁移与双用户测试。实际穿着次数只来源 diary_items；本版不显示推测次数。
